# gojail Threat Model

## 1. System Overview & Scope
`gojail` is a sandboxed execution runtime designed for executing untrusted, LLM-generated, or third-party code. The primary threat actor is an arbitrary code execution payload generated by or passed into an AI agent running inside the sandbox.

## 2. Trust Boundaries
- **Untrusted Zone**: The process execution tree running inside the container namespace and OverlayFS jail.
- **Enforcement Layer**: The Linux kernel (Namespaces, Cgroups v2, Seccomp BPF, iptables/nftables) and the `gojaild` daemon.
- **Trusted Zone**: The host operating system, the host network, host storage, and the `gojaild` management socket / control plane.

---

## 3. Threat Classification & Vectors

### A. Sandbox Escapes (Host Compromise)
- **Threat**: The guest process attempts to break out of namespace isolation to execute arbitrary commands with host privileges.
- **Attack Surfaces**:
  - Unmasked `/proc` and `/sys` filesystem entries exposing kernel knobs (e.g., `/proc/sysrq-trigger`, `/proc/sys/kernel`).
  - Kernel vulnerabilities reachable via unprivileged syscalls.
  - Setuid binary escalation and capability inheritance.
  - Vulnerabilities in shared filesystem drivers (OverlayFS).
- **Mitigations**:
  - Namespace boundaries (`CLONE_NEWPID`, `CLONE_NEWNS`, `CLONE_NEWUTS`, `CLONE_NEWIPC`, `CLONE_NEWUSER`).
  - `PR_SET_NO_NEW_PRIVS` enforced prior to `execve`.
  - Dropping all ambient and inheritable capabilities (`CAP_SYS_ADMIN`, `CAP_NET_RAW`, etc.).
  - Masked `/proc` and `/sys` paths mounted read-only.
  - Strict default-deny Seccomp allowlist blocking dangerous syscalls.

### B. Denial of Service & Resource Starvation (Host Instability)
- **Threat**: Untrusted code consumes excessive host CPU, memory, PIDs, or disk space, degrading neighbor workloads or crashing the host node.
- **Attack Surfaces**:
  - Recursive fork bombs (`:(){ :|:& };:`).
  - Rapid memory allocation causing host out-of-memory (OOM) panics.
  - Infinite write loops filling host disk storage.
  - CPU spinning across multiple cores.
- **Mitigations**:
  - Cgroups v2 strict limits:
    - `pids.max`: Hard upper limit preventing fork bombs.
    - `memory.max`: Container-level OOM killer invocation before host memory pressure.
    - `cpu.max`: Quota and period bandwidth limits.
  - Layered OverlayFS storage quotas enforcing write capacity caps per container upperdir.

### C. Network Abuse & Lateral Movement
- **Threat**: Sandboxed payload attempts to probe private infrastructure, exfiltrate data, perform port scanning, or access cloud instance metadata.
- **Attack Surfaces**:
  - Cloud provider metadata APIs (`http://169.254.169.254`).
  - Internal VPC/cluster services (Kubernetes API server, internal databases).
  - Outbound spam, botnets, or brute-force traffic.
- **Mitigations**:
  - Default-deny egress firewall policy via iptables/nftables.
  - Dedicated network namespaces with virtual ethernet pairs (`veth`).
  - Metadata IP (`169.254.169.254`) explicit blacklisting.
  - Configurable egress destination allowlisting for external package/API access.

### D. Data Theft & State Leakage
- **Threat**: One sandbox session inspects or modifies data belonging to another sandbox session or previous runs.
- **Attack Surfaces**:
  - Reused filesystems or dirty scratch directories.
  - IPC memory segments or shared process trees.
  - Stale mounts and lingering processes.
- **Mitigations**:
  - Per-instance isolated OverlayFS upper/work directories with cryptographic UUID naming.
  - Complete filesystem wipe and unmount cleanup on container destruction.
  - Process group termination (`SIGKILL`) on exit to prevent lingering background daemons.
